# TODO：模型 num_classes (44269) 与实际物种数 (44100) 不一致

> 记录日期：2026-08-19
>
> **已确认**：训练数据确实是 **44100** 个物种，`num_classes: 44269` 是配置写错（非数据缺失、非后来删减）。

## 现象

- 导出的 `onnx/eva02_all_fp32.onnx` 输出 logits 形状为 `[B, 44269]`（44269 类）。
- 但物种映射 `train_map.csv` / `train_map_enriched.csv` 只有 **44100** 行（索引 0–44099）。
- 差值 = **169 类**。

## 根因

- 训练配置里 `num_classes` 是**硬编码的 44269**：
  - `config/large/eva02_all.json:6`
  - `config/large/eva02_all_part2.json:6`
- 而真实类别数是由 `dataSet/SpecialCateDataset.py:29-32` 在训练时**动态扫描数据目录**得到的（`data/train/<类群>/<物种id>/` 排序后从 0 编号，并覆盖写 `train_map.csv`），当前为 **44100**。

## 后果

- ArcFace 头按 `44269 × sub_center(3)` 行建权重，但训练标签只落在 `0..44099`，因此索引 `44100..44268` 这 169 类（`169×3 = 507` 行权重）**从未训练，停留在随机初始化状态**（死神经元）。
- 对推理几乎无害：真实图片的 top-1 必然落在 `0..44099`；死神经元不可能成为高置信 top-1，最多偶尔以低概率混进 top-30 尾部，显示「未知物种 (ID: 441xx)」。
- 当前 `nature-notes-main/infer` 推理服务已切换到该 fp32 模型 + `train_map_enriched.csv`，因此同样带着这个 44269 vs 44100 的差异（服务侧对越界索引做了「未知」兜底）。

## 处理方案（待定）

1. **正规做法**：把两份配置里的 `num_classes` 改为 `44100`，重新训练。
2. **便宜做法**：重新导出 ONNX 时把 ArcFace 头裁到 44100 —— 改 `script/export_onnx.py` 的 `build_from_checkpoint`，把 `num_classes = hp.get('num_classes', 44269)` 改为固定 `44100`，并把 `arcface_loss.weight` 只取前 `44100 × 3` 行再导出。那 169 类是随机权重，裁掉安全。

## 结论（2026-08-19 确认）

- 训练数据就是 **44100** 个物种，`num_classes: 44269` 是配置写错。
- 因此索引 `0..44099` 的映射是**正确对齐**的，那 169 个神经元是纯粹的未训练死神经元。
- 结论：**「便宜做法」（导出时把 ArcFace 头裁到 44100）是安全的**，可直接采用；正规做法（改配置重训）非必需。
